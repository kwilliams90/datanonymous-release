# Sharing policy

datanonymous is intended to provide synthetic files for coding work while original education records stay local. Privacy takes precedence over exact source fidelity. A generated copy requires review of its complete contents and the disclosure context before it is shared.

The requirements below define the implemented sharing release contract. Release acceptance requires independent adversarial evidence and the owner's certainty review. Do not use successful generation or a PASS status as permission to disclose source-derived files. Fidelity mode retains earlier behavior for invented-data work. See the [limitations](limitations.md).

## Disclosure target

The target is that a reasonable person in the school community, without personal knowledge of the circumstances, cannot identify a student with reasonable certainty. FERPA requires removal of personally identifiable information and a reasonable determination considering single or multiple releases and other reasonably available information. Recipient restrictions alone cannot establish that a copy is de-identified. [Department of Education FERPA regulations, sections 99.3 and 99.31(b)(1)](https://studentprivacy.ed.gov/ferpa)

The threshold of 10 distinct people is a project safeguard for individual facts, not a universal legal threshold or a guarantee for joined combinations. The Department does not prescribe a universal disclosure-avoidance method or threshold. [PTAC Disclosure Avoidance FAQ](https://studentprivacy.ed.gov/sites/default/files/resource_document/file/FAQs_disclosure_avoidance_0.pdf)

Fictional joins do not authorize tracking original students. FERPA's coded-record provision in section 99.31(b)(2) specifically concerns education research and imposes additional conditions; ordinary coding work cannot assume that provision applies. [Department of Education FERPA regulations](https://studentprivacy.ed.gov/ferpa)

## Sharing transformations

The sharing mode must be the default and must refuse options that weaken privacy, including forced copying of real factor values, retained titles or flagged names, and a lowered small-cell threshold. There is no policy-exception bypass. Fidelity mode is separately labelled for invented-data work.

Sharing must meet these conditions:

- Each table keeps its row total: N output equals N input. People, table membership, and person relationships are fictional. Keys retain valid joins within a run; aliases, nesting, and composite uniqueness remain valid among fictional entities.
- Each fact table independently reassigns primary-person row counts and equivalent one-to-one aliases, preserving the rows-per-person distribution where it is non-identifying. Secondary person relationships are regenerated rather than inheriting their source count fingerprints. A count class (all the people who hold the same number of rows) held by fewer than `--min-cell` source people is not reproduced, because it could point at one source person; merely assigning that count to another ID is insufficient. Sharing mode instead moves the rows of such rare count classes into the nearest classes that enough people hold ([ADR-0003](../docs/adr/0003-rebalance-rare-count-classes.md)). Every count class in the output is a held class, and the table's row total stays exact. To make that work, the number of fictional people in a table may differ from the source; the private report says by how many. A table is left out only when no count class is held or the row total cannot be met exactly.
- Categorical facts held by fewer than 10 distinct people in a fact table lose their exact counts and rare real labels, including standard educational vocabulary. Merge, suppress, or blur such facts without removing table rows. Reviewed labels with sufficient holders may remain, but their combinations still require assessment.
- Distinct people are counted within each table, by its person column. A table with no person column counts each row as a different person (rows identical in every column count once), unless something suggests that a person has several rows: a column of repeated ID-like keys, or a person-name or e-mail column that repeats a value. With such a sign, the table's columns that need counts of people are Nulled columns, as before ([ADR-0006](../docs/adr/0006-rows-count-as-people-without-repeats.md)). Row counts stay in their own table: they never raise the holders of a value in another file. The private report lists every table whose rows were counted as people under "What needs attention", with the `--person-id` fix for a table where someone can have several rows.
- Dates attached to personal records exclude whole public calendar groups containing source extrema, with enough local distinct-person support for each revealed boundary group. Month and season classes remain where supported. Source-inferred weekdays and day grids are discarded; exact source-membership calendars and infeasible constraints cannot be written (see [Columns sharing mode cannot protect](#columns-sharing-mode-cannot-protect)). Coarse endpoint intervals remain observable. Numeric minima and maxima may remain only when at least 10 distinct people in that fact table hold them (use a higher configured threshold when set). Rare interior discrete numeric values lose their exact counts the same way, and every discrete numeric column gets this protection whatever its formatting ([ADR-0002](../docs/adr/0002-one-rare-value-rule-for-all-numerics.md)): plain integers, currency, grouping separators, suffixes, parenthesised negatives and zero-scale decimals are parsed, their rare values and extremes are removed, and the remaining numbers are written back in the column's own format. A column left with no safe numbers is not written as data (see below).
- IDs whose values are exactly 1 through n keep that set with randomized assignment and consistent fictional joins. When a table is left out, this is decided over the written tables' IDs alone: values that are no longer exactly 1 through n are replaced like other identifiers. Other replacement identifiers must avoid source identifiers within their applicable namespace. An unpadded numeric identifier length held by fewer than `--min-cell` IDs is not reproduced: those IDs take the nearest length that enough IDs hold. In the same way, an identifier format class (a layout of letters, digits, punctuation or hex) held by fewer than `--min-cell` IDs, including a minority layout in a mixed column, is written in the column's most common held format class ([ADR-0004](../docs/adr/0004-rare-formats-take-broader-held-classes.md)). A column with no held format class is still refused, and so is a column of e-mail-address IDs.
- Text shapes (such as `AA-0000`) and date formats held by fewer than `--min-cell` people are broadened rather than released. A rare text shape is first written as the same shape without its leading-digit and length detail, then, if that is still rare, in the column's most common held shape. A rare date format is written in the column's most common held date format. The private report's "What changed" lists the column. If no held class exists the column cannot be written. A shape defined by embedded personal information is never broadened: such a column is a Nulled column.
- Synthetic phones may look ordinary and use exchanges other than 555. No generated phone may match any source phone anywhere in the run, including alternate formatting or embedded numbers. Preserve useful formatting and area-code distributions only when collision-free generation permits it.
- Existing protections for names, email addresses, personal identifiers, addresses, free text, and metadata continue to apply. An unrecognized identifying value is a defect to remediate, not an approved exception.

Person support must describe the person who owns the attribute. Twenty students
sharing one parent's name do not supply twenty parent donors. Sharing currently
cannot release recognizable intrinsic attributes of parents, guardians, teachers,
staff and other people when actor ownership has not been established. Such a
column is written as a Nulled column (with `--refuse-unsupported`, the file is
left out instead); you can also exclude it. A subject-key flag alone cannot
establish ownership of another person's attributes.

The intended retained joint structures are fictional join coverage, one-to-one key aliases, nesting, composite-key uniqueness, regenerated within-person constants, approved dependencies and templates, safe missingness patterns, and declared temporal rules. They support code compatibility; source membership, original family or staff relationships, source timelines, and undocumented person fingerprints are not part of the contract.

## Columns sharing mode cannot protect

When sharing mode cannot protect one column, it nulls that column and writes the rest of the file ([ADR-0001](../docs/adr/0001-sharing-nulls-unprotectable-columns.md)). A Nulled column keeps its header and position and has every cell missing; its real values are recorded as dropped, so no generator writes one and the leak scan looks for them. Two things trigger this:

- A column-level refusal while the column is profiled for sharing or while its values are generated: too few people support its values, its table has no person column and a sign that a person has several rows, the column describes another person, its numeric support disappears once rare extremes are removed, its dates have no safe cover, its rare values are tied to a rule, or it has a shape defined by embedded personal information.
- A blocking finding about one column after the file is generated, such as a number column that looks like an ID or code but is not used as a key, or a leak-scan hit in one column. The file is then generated again with the same seed and checked again. If nulling does not clear the findings, the file is left out instead of looping.

Nulling applies only to a column that is not a key and is not in a relationship that reaches past its own values. A key, an alias, a nested column, or a column in a join, composite key or declared rule would break the joins the copy exists to keep, so a problem there still leaves the file out. A relationship inside one table, a dependency (a join year fixed by the year of study) or a template (an e-mail address built from name parts), breaks no join, so its column is nulled like any other and the relationship is not kept. When a column is refused because of such a relationship, the side that depends on it is nulled first: the dependent column, or the column the template builds. A finding about whole rows or the whole file (rows that match real rows, a leak scan that could not finish) still withholds the file, because nulling one column does not answer it.

The private report lists each automatically Nulled column under "What needs attention" with the plain reason, and keeps it apart from columns you nulled with `--null`. A relationship inside the table that nulling lost is listed under "What changed", for example "the link between YearofStudy and Yr_JoinCampus is not kept"; the shareable README says only that a link between columns is not kept. For a column that looks like an ID, it suggests declaring it with `--id-col` (or `--person-id`) instead. A run whose only problems are automatically Nulled columns exits 0 and counts the file as written for `--all-or-nothing`. `--refuse-unsupported`, also accepted as the config key `refuse_unsupported`, turns this off: every such file is left out, the run exits 3, and `--all-or-nothing` writes nothing. The option never weakens privacy; it only makes sharing mode stricter.

When protection costs fidelity, the order is: release no real or rare value, keep keys and joins valid, write the file, and only then keep distributions close to the source ([ADR-0005](../docs/adr/0005-skew-distributions-before-refusing.md)). Distributions after count-class rebalancing, format broadening or rare-value merging can therefore differ from the source.

## Package requirements

Use a new or empty output folder outside the inputs and reports (the local report folder may sit inside the inputs). Both destinations are labelled so the private one is never mistaken for the shareable one: the console names them "Shareable synthetic files" and "PRIVATE report - do not share" at the start and end of a run, `REPORT.md` opens with a `PRIVATE – DO NOT SHARE` banner, and the report folder holds a `PRIVATE-DO-NOT-SHARE.txt` marker. The marker is never written to the output folder. Write only a validated inventory of synthetic tables and reviewed synthetic-derived documentation. Source profiles, mappings, assignment details, source comparison reports, temporary files, stale files, and unrelated artifacts are excluded. Read and validate every included artifact, including filenames, headers, sheet names, container metadata, workbook properties, value labels, and compressed members. An unsupported, unreadable, unverified, or unreviewed input file is left out of the output folder and listed, with its reason, in the report folder's `sharing-failures.csv`; the output's README counts the files left out without naming them, and fictional joins hold only among the files written. A key-population refusal traced to particular tables (a rows-per-person count that cannot be rebalanced, an identifier column with no held format class, an infeasible join) leaves those tables out; the remaining tables are planned again over the people they hold, and a join whose target is left out is dropped rather than the table that refers to it. A key-population refusal that no single table answers for leaves every table out. A file that fails or is withheld after planning is left out and the remaining files are planned and written again without it, so no plan assumes it was written. A problem that concerns the whole run (an output folder whose contents cannot be verified, a leak scan that did not complete, a column option or rule that applies to a written file but was not applied) writes nothing.

A file with an unresolved privacy warning that cannot be answered by nulling a column is not written. Other warnings must satisfy their stated utility or validation criteria. A run that leaves files out exits with code 3 (a Nulled column is not a file left out); `--all-or-nothing` writes nothing unless every selected input file is written and none is skipped (a file that `--include` or `--exclude-path` leaves out is not selected). The operator must review the files left out and the skipped inputs, and review schema and paths because automated name screening has gaps.

## Technical acceptance and deployment

Release evaluation uses a canonical wholly invented original. An adversary receives that original, its generated copy, and the public repository and attempts direct and partial linkage across files. Any demonstrable source identity or donor link blocks release and requires remediation. Coincidental equality must be distinguished from linkage using recorded attacks and false-match baselines.

A separate gpt-6-astra assessment receives the synthetic copy and repository and states what it can determine with certainty about the original. The owner judges those results against the reasonable-person target. This judgment remains required; automated checks do not replace it. Record versions, transformations, tested scenarios, failures, and uncertainty as technical evidence.

Public software release requires implementation, reproducible evidence, useful code contracts, and accurate documentation. It does not require a district customer, institutional legal approval, or vendor agreement. Institutions adopting the tool remain responsible for their own authorized access, recipients, applicable rules, and disclosure decisions. Follow the [operator guide](operations.md) for those deployment steps.
